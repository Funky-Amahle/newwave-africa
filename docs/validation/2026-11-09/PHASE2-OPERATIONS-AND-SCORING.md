# Phase 2 — Reader and creator validation operations

**Prepared:** 9 November 2026 SAST | **Status:** STUDY NOT RUN | **Current production candidate:** `a1ae9260848f3a574866f7820a3285a03d1b2539`

## Objective and decision

Validate readers' meaningful discovery and explanation comprehension, and creators' independent ability to draft, confirm rights, save and retrieve a browser-local original/fictional story. Do not claim an impact study, a representative African population sample, AI personalization, or live publishing.

Separate three evidence types: (A) 144 synthetic ranking comparisons already generated by the pinned benchmark, (B) real 10-reader and 10-creator usability tasks NOT YET COLLECTED, and (C) separate blinded judgments on >=80 rights-cleared works and >=40 search intents NOT YET COLLECTED.

## Consent, recruitment and storage

- Recruit 10 readers R01–R10 and 10 creators C01–C10 voluntarily, spanning reading needs, creative practices, language preferences and accessibility needs where possible. Report sampling gaps; never infer representativeness from n=10.
- Explain before the test: NewWave Africa currently uses fictional stories, deterministic local ranking, browser-local drafts and optional separate providers. Tasks may be skipped or stopped without penalty.
- Use only fictional content for creator tasks. Do not request real unpublished stories, identity documents, health information, API keys or actual private audio. Voice recording is optional and needs independent consent.
- Store signed consent and any session recordings separately from task outcomes in an access-controlled, non-public research location. Decide retention and withdrawal handling before recruitment. The repository stores only protocol, empty form and scoring code.
- A person facilitating the research must verify consent. The scorer checks a consent flag but cannot authenticate a participant's agreement or a recorded observation.

## Runbook

1. Freeze an exact production git SHA and the successful deployment run. Confirm participants are testing that same deployed build. Keep a stable device/browser record in private study notes.
2. Conduct the already-approved task definitions in [Reader/Creator Protocol](READER-CREATOR-STUDY-PROTOCOL.md): each reader R1–R5; each creator C1–C5.
3. Randomly assign five readers to see baseline (0%) first and five to see diverse (60%) first for R3. Record order and preference. This is an illustrative fictional comparison, not real relevance or preference generalization.
4. After R4, ask the reader independently to explain: (a) recommendations are deterministic local scoring, not learned from their behavior; (b) listed examples are fictional; (c) drafts/bookmarks are browser-local, not publicly posted. Record each yes/no without giving hints.
5. For creators, only a participant who completes all C2, C3 and C4 with no facilitator help counts toward the primary creator success threshold. Record rights misunderstanding or attempted unauthorized save as an issue, even if the session otherwise succeeded.
6. Capture exactly one task row per participant (100 total) using [the structured CSV template](PHASE2-STRUCTURED-CAPTURE-TEMPLATE.csv). Store completed records under `private-research/` **locally, not in Git**. The previous rich-text capture template is still usable for restricted field notes but must never be committed with participant observations.
7. Run the local scorer and save the aggregate JSON privately; do not upload individual rows or derived small-group identity details.

```sh
node scripts/research/score-phase2-study.mjs --input private-research/phase2-study.csv --release-sha a1ae9260848f3a574866f7820a3285a03d1b2539
```

Note: CLI exit 0 means recorded formative thresholds passed; exit 2 means incomplete or failed thresholds; exit 1 means invalid input. It does not independently prove attendance, consent, authenticity of observations or statistical representativeness.

## CSV dictionary

| Field | Allowed values or definition |
|---|---|
| `participant_id` | R01–R10, C01–C10 only. Pseudonyms; maintain recontact codes separately. |
| `task_id` | R1–R5 or C1–C5 matching participant role. |
| `consent_confirmed` | yes/no; if no, task must be `not_tested`. |
| `completion` | yes/no/not_tested; record no for attempted but unfinished. |
| `seconds_to_complete` | 1–7200 integer for attempted tasks; blank for not_tested. |
| `help_requests`,`error_count` | Non-negative integers. |
| `privacy_or_rights_issue` | none/significant/critical. |
| `severity` | none/P0/P1/P2. |
| `model_understood`,`fictional_understood`,`local_draft_understood` | yes/no/not_tested for R4 only, blank otherwise. |
| `condition_first` | baseline/diverse for attempted R3 only, otherwise blank. |
| `list_preference` | baseline/diverse/neither for attempted R3 only, otherwise blank. |

**Do not add names, locations, age, genders, direct quotes, phone numbers, email addresses, or unreviewed free text to the structured CSV.** This restricted format intentionally reduces leakage and prevents accidental publication.

## Preregistered success/failure decisions

- **PASS only if** all 100 task rows are recorded for consented participants, no tasks skipped, R3 presentation order is exactly 5/5, >=8/10 creators completed C2–C4 unassisted, >=8/10 readers correctly explain all three R4 concepts without help, and zero recorded critical privacy/rights or P0 events.
- **FAIL** if a critical event is recorded, or if complete evidence misses any threshold.
- **INCOMPLETE** when expected rows, consent or attempts are missing. Never interpret INCOMPLETE as PASS.
- Capture descriptive task-level completion counts and medians; avoid significance or representativeness language.
- Review serious/critical comprehension problems individually before adopting product copy changes. Do not unblind or cherry-pick failed users.
